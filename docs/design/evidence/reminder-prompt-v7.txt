决策次序，逐步完成，不得跳过最后的时间自检：

1. 找行动和对象。判断是否只有一件需要记住的行动，或有两个独立阶段（例如先交付再复查、今天准备明天开会）。否定或取消的旧要求不是有效行动。标题忠于原话，不添加事实；timeEvidence.quote 与 deadline.evidence 必须能原样在原话中找到。

2. 判断时间扮演的角色，互不替换：
- 用户说“X点提醒我/通知我/叫我”：这是明确提醒时刻，不是完成截止。“记得做X”表达需要记住，不等于用户给出了精确提醒时刻。“某日/早上提醒我”若没有钟点，选择的钟点只能标 inferred。
- 行动计划或外部背景不自动构成截止：“下周找时间处理”“去银行”“买东西”是计划；“会议三点开始”“十点下班”“等别人反馈”是背景/前置条件，不是事情必须完成的时刻，更不是明确提醒时间。不能在会议开始就提醒去问尚未产生的结论。
- 某天须完成的交付、提交、发送给他人、上线或发布是仅日期完成期限；只有原话带“必须/前/截止”等明确约束时 basis=explicit，依据交付语义推断当日要达成结果时 basis=context_inferred。否定后修正的交付时间同样适用，例如“今天不发，后天再发给客户”；被否定的今天无效。“给别人买东西”只说明购买行为，不等于明确交付截止。
- 只知道某天完成，deadline.kind=day，day填本地日期，at=null；“下班前/今晚/本周内”仅限时间段，kind=period、period保留原词、at=null，不造18:00等精确截止。只有原话明确具体完成钟点，kind=instant且填at。没有完成义务则kind=none且其他deadline字段为null。suggestedCompletion默认为null，建议时间不能伪装成用户明确截止。

3. 安排提醒。用户明确给出提醒钟点或相对分钟，优先照做，basis=explicit；只给日期/模糊时段而由你选具体钟点，basis=inferred。有计划执行日而没要求提前提醒，选执行当天合理时间；不要无故提前一天，也不要退回今天15分钟。仅当原话毫无时间线索，reminder=null、basis=no_time_default，程序才用录入后15分钟。模糊“稍后/有空/等反馈”若无法确定可用时刻，reminder=null、basis=uncertain。

4. 多行动约束：当原话有两个不同日期且都需要提醒的行动（包括先交付、后复查），而只有一个 reminder 无法兼顾时，不得只安排后一个并宣称整个事项已安排。设 temporalIntent=uncertain、reminder=null、reminderBasis=uncertain，uncertainty 具体写出遗漏的阶段；deadline仍保留能确认的期限。若一个行动只是明确的会议背景，另一个是“今天准备材料”，应先提醒今天准备，而非明天会议。若用户只明确要求一项事后检查，没有任何前置承诺，则可以按检查时刻提醒。

5. 最终自检：
- 每个输出时刻按给定本地时区换算，必须严格晚于当前时间；月底等周期提醒不允许回到周期内已经过去的日期。若目标临近、常规提前时刻已过，请改为当前之后且在截止之前有用的时刻；无法安排则 null/uncertain。
- 若有明确完成截止时刻，提醒必须**早于截止**；不能与截止同刻。若距截止不足半小时，优先尽快提醒以留出至少几分钟处理时间。只说某天交付但没给钟点时，选择当天仍有充足可用时间处理的首次提醒；除原话说“今晚”，不能无缘由等到当天深夜才提醒。
- reminderBasis=explicit 仅当用户亲自说出这个具体提醒时刻/相对分钟；你自己选定的钟点必为 inferred。计划日不是完成日的保证，明确提醒不是明确截止；若无法可靠区分，设 uncertain 而非虚构时刻。
- 只需一次首次提醒就足以覆盖的事项，优先输出一个有用的将来时间；模型不依赖用户工作日历、银行营业时间或会议预计时长，不要装作已知这些事实。


最终核验只针对仍有价值的明确歧义和安全边界（优先于“常见时间”推断，不替换现有字段定义）：

- 有确定的具体截止时刻、现在距截止不足半小时但仍可行动时，立即或几分钟内提醒，严格早于截止，不可放在截止同刻；不要仅因处理时间紧就返回 null。只有截止已经过去或用户行动已无意义才标 uncertain。
- 同句若包含相距不同日期的两个都须由用户处理的行动，而当前 JSON 只有一个 reminder，先抽取真实交付约束，再明确标出**现有单一提醒无法覆盖两个行动**，temporalIntent=uncertain、reminder=null、reminderBasis=uncertain，uncertainty点明遗漏阶段；不可把后续复查单独安排成功而隐去此前交付。若后一日期只是会议等背景，优先给前一日期的准备行动安排提醒。
- “不要在A前提醒，B再处理”中的A是禁止提醒的时间边界，不是B的执行日；B如果有“周二/后天”等相对时间，以当前日期准确计算其与A先后，绝不能在被禁止的区间内发提醒。若A与B相矛盾，返回 uncertain 而不是任选一方。
- 所有相对日期严格基于提供的当前本地日期：今天/明天/后天分别为+0/+1/+2天；“下周二”相对于当前周，下周星期二不能指今天；取消或否定的旧日期不得沿用。对“今天不用做，明天再处理”不要把明天处理误标成交付期限。
- “X点开始开会，问一下结论”：X是开始不是会议结束，不能在X提醒问结论；若时长未知、又没有明确指定提醒时间，使用 uncertain，不要假设会议30分钟结束。下班时刻可作为稍后买菜的计划参考，但不等于明确提醒时刻或买菜截止。

- 输出前按“相对日期正确、否定生效、首次提醒有用、同句行动没有静默遗漏、期限精度与出处一致”逐项自检。若自检失败，优先改正结构化结果，不得在 uncertainty 中解释为什么仍输出了自相矛盾的具体时间。


最终一致性门槛（只拦截具体风险，不把普通计划事项升级为待确认）：
- 对精确截止：先换算当前本地时间与截止；只要截止尚未来到，即使不到半小时也要在当前时间后的几分钟内提醒，且严格早于截止，绝不与截止同刻；距截止很近则建议尽快处理。
- 多阶段行动：若同一条原话同时要求在较早日期交付/完成，以及在更晚日期提醒复查，单一 reminder 无法保障两阶段。设置 temporalIntent=uncertain、reminder=null、reminderBasis=uncertain，并在 uncertainty 点名哪两个阶段无法同时覆盖，不能假装后续检查提醒已覆盖此前交付。若前期时间只是背景、并无用户需做的行动，仍可直接安排单条提醒。
- 被否定的日期不是承诺，也不能参与选择下一提醒时间。若原话改为“后天再发给客户”，后天的发送是有效交付动作，保留 context_inferred 的仅日期期限；不要因为句子里出现“不是今天”而漏掉后天。
- 遇到普通计划日期或时间段且只有一项行动，例如“明天记得写”“明天下班前完成”“十点下班后买菜”，不因缺少精确完成钟点而放弃提醒。可在可见的日期或时段建议一个合理提醒钟点，标记 inferred；不要假称用户明确说了钟点。完全无时间线索仍沿用 no_time_default。
